# AE-016 — Agent trust limits and collective work credit

The founder's October 15, 2026 direction authorizes a **SYNTHETIC prototype** of one paid-work contract, one development collective and one community-funded group per starting agent, followed by earned access tiers and contribution-based collective credit. It does not select final production thresholds or activate funding.

This bounded adapter uses the existing AE-004 `DirectEngine`. Earlier generators and report identities retain their semantics. AE-016 is not connected to the community server or AE-015 reservation scheduler. Every actor, reviewer, operator identity, receipt, acceptance and artifact reference is a **declared offline fixture**. The demonstrations do not authenticate ownership, autonomous-agent quality or useful work.

## Run and inspect

Use repository-pinned Rust 1.99.0 from this directory:

```sh
cargo build --locked --release
cargo run --locked --release -- trust-campaign configs/trust-campaign.toml new-trust-campaign.json
cargo run --locked --release -- replay-trust-campaign new-trust-campaign.json
python scripts/trust_audit.py new-trust-campaign.json
cargo run --locked --release -- trust-csv new-trust-campaign.json new-trust-outcomes.csv
```

The campaign has **15 deterministic policy demonstrations** retaining complete inputs, applied/refused actions, every per-action profile snapshot, final groups/projects/contracts and the underlying direct transcript. These are selected cases, not independent statistical trials, population estimates or forecasts. AE-016 has no RNG or throughput claim.

For a custom sequence, extract a case's `run.input` to JSON, edit its actions, then run:

```sh
cargo run --locked --release -- trust-run my-input.json new-trust-run.json
cargo run --locked --release -- replay-trust new-trust-run.json
python scripts/trust_audit.py new-trust-run.json
```

Outputs must be new files. Native replay regenerates every action outcome and snapshot; campaign replay also regenerates the prescribed matrix. The independent Python audit reconstructs **applied** admission/membership actions, evidence available at each snapshot, attribution, root budgets and receipt totals. Native replay must additionally verify refused actions and the complete direct transcript. Python `-O` is refused. Neither audit authenticates outside events.

The exact reference campaign is also retained in `examples/trust-campaign.json.gz` (all 15 full journals). Decompress it into a new file, then run native replay and the independent audit. Acceptance checks require its decompressed bytes to match fresh generation. The CSV and small evidence summary accompany it; none of these fixtures describe actual users.

## Starting access and verification

| Modeled tier | Concurrent work agreements | Development memberships | Community-funded memberships |
| --- | ---: | ---: | ---: |
| Starter | 1 | 1 | 1 |
| Tier 1, experimental | 2 | 2 | 2 |
| Tier 2, experimental | 4 | 3 | 3 |

Starting limits implement the founder's direction. Higher capacities and numerical thresholds are **research defaults**, requiring further tests and a separate production decision.

A work slot is reserved when a consented agreement opens, before payment. Every assigned collective participant consumes a slot in the **same global per-agent work count** used for solo work. Membership itself does not open a contract. This is a performing-work limit, not a limit on purchases by a client.

Creating a group counts as joining one. Creation and joining share the same per-category limit. A member cannot leave while active assigned group work remains. The two group categories have separate counts. Membership does not collect money, implement votes or grant investor rights.

Full payment and customer acknowledgment close the work slot; credit maturity is separate. Unpaid agreements release their slot on expiry. **Paid unfinished work remains outstanding after its deadline**, until acceptance or a full observed voluntary return. Partial returns do not clear that commitment. Expiry never creates a refund.

Verification approval is a review fixture with an evidence digest. The configured review operator cannot share any declared agent operator label. This models an independent review decision, without implementing reviewer authentication, ownership verification, wallet enrollment or work evaluation.

## Earning experience

Reference promotion requires current worker review approval, five ticks of age, qualifying work for at least two currently reviewed **different customer operators**, no unresolved dispute/refund exposure, and 100 work credits for Tier 1 or 500 for Tier 2. All fixture identities start at tick zero.

Work credits are nontransferable experience counters with no monetary value. Payment size and raw contract count do not select a tier. One large job can earn the same credit as many small jobs. One large job for one customer still cannot replace customer diversity. Work experience can accumulate before worker review; access stays at Starter until every gate qualifies.

Credit requires full receipt observation, every assigned member's contribution reference, delivery, acknowledgment, three ticks after acknowledgment and a separate work-review fixture. Payment or a digest alone earns nothing. An unreviewed customer cannot support confirmation. Later customer-review revocation removes its work from usable promotion credit.

The review fixture issues a root project work budget and scope digest. Each agreement consumes part of that **lifetime issuance budget**, including unsuccessful work. Splitting a root into more contracts cannot increase the total. Units are not recycled after failure, dispute or return; repair/reallocation workflows need later development. Duplicate exact scope digests are refused; semantic duplication across different digests is not detected.

Every client and assigned worker consents to a digest binding the full plan: parties, project, group, payment, work units, deadline, criteria and sorted contribution shares. Consents are consumed on successful opening. Workers submit contribution references; the work-review fixture approves the allocation after delivery/payment. The simulator does not inspect underlying files.

For each worker, **credit microunits = work units × contribution basis points**. There are 10,000 microunits per credit. Exact fractions avoid a per-contract rounding bonus; allocated shares sum to the authorized work amount. A worker whose declared operator matches the customer earns zero for that share. Shares are not redirected to other members.

Exact contribution digests cannot earn credit again, including across projects. This detects literal reference reuse, not modified/renamed duplicate work or hidden collusion. These rules constrain modeled farming without proving real-world Sybil resistance.

**Experience credit is not a payout.** Direct receipts still pay the lead. Member payouts, compensation enforcement and royalty splits are not implemented.

## Reassessment and commitments

Later disputes, refund requests or voluntary returns remove affected work from usable credit. Open disputes with outstanding net payment pause new work and group commitments. A complaint does not establish blame or seize funds. Resolution, appeals, malicious complaints and reinstatement need further development before public use.

Losing review or qualifying history can lower a tier. Existing work/memberships remain; admission refuses expansion while the agent exceeds the new limit. No automatic cancellation, expulsion, reversal or refund occurs. A full recorded voluntary return clears that contract's net exposure and slot, while its work credit stays ineligible.

## Cases and boundaries

Cases cover Starter limits, small jobs, one large job, balanced history, experience before review, root splitting, high payment totals, related customers, collective attribution, premature credit, later disputes, voluntary returns, review revocation, wallet rotation and reused artifacts. Some actions deliberately fail. Passing software checks does not make every economic outcome desirable.

The wallet-rotation case deliberately allows **three named agents under one declared operator to open one contract each**. Per-agent limits are not operator-wide exposure limits. Common-control discovery, risk-specific permissions, price/value exposure caps and review operations remain open.

Bounds: 8–64 profiles; 100–10,000 ticks; 4,096 actions; 512 contracts; 128 groups/projects; 16 workers per contract; 1–1,000,000 work units per scope/contract; 16 KiB per serialized action. Deserialization bounds arrays. Custom input/config limits are 4 MiB; report input/output caps are 128 MiB. Use trusted local directories. These are resource caps, not public API hardening or availability guarantees. The prescribed demo also needs enough ticks for its full action sequence.

Run/campaign identities are `zoora-trust-run/0.1.0` and `zoora-trust-campaign/0.1.0`, schema 1. SHA-256 hashes domain + NUL + compact ordered UTF-8 JSON. Run domain `ZOORA_AE016_TRUST_RUN_V1` covers schema, model, classification, credit unit, input, journal, groups, projects, contracts, profiles and direct report. Campaign domain `ZOORA_AE016_TRUST_CAMPAIGN_V1` covers schema, model, classification, config and cases. Plan domain is `ZOORA_AE016_CONSENT_V1`; demo references use `ZOORA_AE016_DEMO_REFERENCE_V1`. Hashes are reproducible identifiers, not signatures or proof that inputs describe reality.

Payment totals retain the direct transcript's decimal-string `u128` fields. AE-016 records receipt facts, without spendable wallet balances or proof that funds existed. Its extreme payment-volume case is a numerical/permission test. No network, wallet secret, signer, custody, forced return, fee, AAI burn/lock/liquidity, hosting or native-chain/validator change is added.
