# AE-013 — Payment evidence and funded work queues

This is a new, versioned **SYNTHETIC / SIMULATED_UNITS** timing experiment in the existing economy laboratory. It separates three things: an actual transfer in the synthetic wallet model, when evidence of that transfer becomes available, and permission to occupy work capacity. The existing AE-004 direct agreement adapter is reused. AE-012 reports, fee experiments and schemas retain their semantics and fingerprints. No production service, signer, custody, consensus, validator or native token policy is changed.

## Run and inspect

From `projects/zoora-agent-economy-simulator/review`, with pinned Rust 1.99.0 and Python 3.11+:

```sh
cargo build --locked --release
python scripts/run_economy_campaign.py --model payment --config configs/payment-campaign.toml --output-dir target/my-payment-campaign
```

This retains every complete run in `runs/` and creates `campaign.json`, `campaign.csv`, `campaign.html` and `progress.json`. Open the HTML locally. It is an offline viewer, not a deployed start/control surface or proof of actual iPhone/Safari operation. No network, wallet keys, accounts or paid infrastructure are needed by the compiled runner; installing development dependencies needs internet.

To pause deliberately, append `--max-new-runs 3`. To continue that directory, use the same command with `--resume`. The same executable digest and exact config bytes are required. Cached full runs must replay; changed configs/executables and corrupt evidence stop completion. Native files are created exclusively. Completed files are published from same-filesystem staging with exclusive hard links; use one coordinator per trusted local directory with hard-link support. Only the coordinator's own progress file is replaced atomically. A partial run remains INCOMPLETE. The default model remains `economy`, preserving the AE-012 command interface.

Summary-only and individual-run CLI:

```sh
cargo run --locked --release -- payment-campaign configs/payment-campaign.toml new-campaign.json
cargo run --locked --release -- replay-payment-campaign new-campaign.json
cargo run --locked --release -- payment-run configs/payment-campaign.toml 42 OBSERVATION_LAG EVIDENCE_GRACE new-run.json
cargo run --locked --release -- replay-payment new-run.json
python scripts/payment_audit.py new-run.json
cargo run --locked --release -- payment-csv new-campaign.json new-campaign.csv
cargo run --locked --release -- payment-viewer new-campaign.json new-campaign.html
```

The Python audit independently reconstructs arithmetic, backing facts, cutoff causality, FIFO and provider capacity. It is not scenario regeneration or external receipt authentication; use native replay as well. It refuses Python -O so assertion removal cannot silently bypass the independent checks. Output filenames must be new in existing directories. Summary rows retain metrics, per-round results, run fingerprints and at most twelve sampled stress observations. Full runs retain every quote, transfer fact, observation, queue event and direct-adapter record.

## Controlled experiment

The supplied config has ten seeds, eight scenarios and three policies: **240 unique configurations**. Each has 24 declared profile IDs, 12 rounds, 36 ordinary requests per round, four work slots per provider, 200,000 opening units per profile, a price of 1,000 units, a four-tick funding window, six additional evidence-grace ticks and two service ticks. This study has **zero fees**, isolating timing and work admission from AE-012's separate illustrative fee sensitivity.

The first half of IDs are providers; the next quarter are ordinary clients; the last quarter are attacker fixtures. These are declared model roles, not authenticated identities. An attack flag controls fixture behavior and metrics only. Receipt eligibility and work scheduling do not inspect it. The ordinary outcome assumption remains 60% client-acknowledged digest, 10% refused return, 10% full voluntary return, 10% half voluntary return and 10% no delivery. These are scripted assumptions, not measured AI quality.

The full potential plan is drawn once with pinned ChaCha8 and hashed before any admission. It includes possible attacker requests in every round. Scenarios select their described intervention; policies never redraw intentions. All three policies and all eight scenarios share a plan fingerprint per seed. Config-dependent quote admission can change whether a client actually sends a payment; rejected intentions are not represented as paid work. The new timing model is a distinct experiment, so its counts should not be compared directly with AE-012 as if only one parameter changed.

| Scenario | Intervention in the middle third of rounds |
| --- | --- |
| NORMAL_DELAY | No shock. Clients send at round offset +1; receipts are available one or two ticks later. |
| UNPAID_SYBIL_FLOOD | Separate attacker profile IDs request all provider capacity before ordinary demand, then never pay. |
| PAID_SYBIL_FLOOD | Same requests and order, but attackers pay, obtain work slots and never deliver. |
| OBSERVATION_LAG | Ordinary transfers are sent at +1 but evidence arrives at +7. The transfer was timely; observation was delayed. |
| LATE_PAYMENT | Ordinary clients actually send at funding cutoff +1, with the ordinary observation delay. |
| DUPLICATE_RECEIPTS | Repeat ordinary payment observations at the same availability tick without another transfer. |
| OUT_OF_TERMS | Ordinary clients actually transfer price +1. The quote-bound direct adapter rejects the overpayment; the wallet fact remains. |
| UNBACKED_CLAIMS | Attacker profiles submit receipt-shaped claims with no corresponding transfer fact. |

Normal and recovery phases still have ordinary outcomes and natural capacity failures. Profiles do not earn new client income, dynamic prices are absent, and there is no AMM, gas, slippage, market price, actual chain finality or trading model.

## Three admission policies

| Policy | What occupies work capacity |
| --- | --- |
| RESERVE_ON_QUOTE | A successfully admitted quote reserves a slot immediately, including unpaid reservations. Paid jobs begin only when valid evidence arrives and time remains. |
| STRICT_OBSERVATION | Quotes are bounded metadata only. A backed, adapter-accepted payment must both be sent and be observed strictly before the funding cutoff. |
| EVIDENCE_GRACE | Quotes are metadata only. The transfer must be sent strictly before the funding cutoff; evidence may arrive strictly before funding cutoff + grace. |

Funded policies allocate slots in receipt-validation order, independently per provider. The scheduler never labels a payer trustworthy because it knows the fixture's attack role. An actually late transfer cannot become timely through grace. All policies require enough remaining time for service and client acknowledgment before the delivery deadline. A digest alone does not release capacity: acknowledgment or a fully observed voluntary return releases it; failed/missing work can hold the slot until the deadline. This is a research queue, not a live community permission change or a proof that any policy is production-safe.

Nonpaying profiles cannot occupy funded work slots. They still consume bounded quote metadata. Paying attackers can occupy slots, and legitimate clients may pay into a queue that misses its delivery window. These limitations are reported explicitly. The experiment does not establish common control, solve Sybil identity, authenticate real funds or prevent paid denial of service.

## Time, transfers and observations

Round r begins at tick `3 + 16r`; quotes share that tick. Delivery deadline is round start +13; the final completion tick is 194 for twelve rounds. Cutoffs are **exclusive**. At each tick, scheduled work actions and deadline releases run, transfer fixtures are sent, available observations are validated, and then funded jobs are dispatched. At equal availability time, fixture insertion order breaks ties; attacker transfers are deliberately ordered before ordinary transfers. FIFO uses validation sequence, not a hidden attack-quality label.

The ledger debits and credits a transfer exactly once at its simulated send tick, including funds awaiting observation. Every balance stays nonnegative, and total wallet units conserve after each transfer. No observation, duplicate claim, rejected admission or deadline performs another debit, reverses a transfer or creates a forced refund.

The observation adapter first requires the entire receipt to match a known synthetic transfer fact. A matching source string alone is not backing. Backed facts are deduplicated by transaction reference before forwarding to the direct agreement adapter. Even a quote-policy rejection or missed window leaves the transfer in the wallet ledger. The existing adapter's rejection, such as an overpayment exceeding quoted amount, is retained separately. This supplies an evidence-preserving comparison around that quote-bound adapter; it is not a new real-chain verification adapter.

Voluntary returns are separate sender-authorized fixtures. A complete return releases capacity after its observation is accepted, not by erasing the original payment. A deadline can release work capacity while later permitted return observations remain recordable. The synthetic receipt uses simulation/availability ticks, no chain slot and SIMULATED_FINAL provenance. There is no real timestamp or chain-commitment claim.

## Metrics and reconciliation

The model records ordinary work intended/quoted/paid/started/acknowledged, attack requests/quotes/payments/starts, metadata and work-capacity refusals, insufficient budgets, unbacked claims, duplicate observations, adapter refusals, late transfers, late evidence, paid ordinary work never started, and peak per-provider occupied/ready-queue counts. The reported acknowledgment denominator is **all intended ordinary work**; it never includes attacks or removes refusals.

`opening_units = final_wallet_units` in this zero-fee transfer model.

`payments_sent = adapter_payments_recorded + observed_unapplied_payment_units`.

All fixtures have been observed by completion. The second equality includes overpayments retained in wallet truth but rejected by the agreement adapter. Returns are separately reconciled against accepted direct return receipts. They are not extra income. `paid_not_started_net_units` sums remaining net payment for all quotes never started, including attack fixtures. `unacknowledged_net_units` sums net payment without client acknowledgment. Neither is independently verified real-world loss or profit. Full-return observations reduce exposure; disputes and refusals do not move units.

Round counts/flows retain their own denominators; opening/final wallet stocks repeat the conserved stock, while flows are round-specific. Peak counters aggregate by maximum, other counters/flows by sum. Pooled values across seeds are totals across separate experiment replicas, not one economy, a confidence interval or an adoption forecast.

## Integrity and bounds

Models are `zoora-payment-run/0.1.0` and `zoora-payment-campaign/0.1.0`, schema 1. SHA-256 hashes the domain + NUL + compact UTF-8 JSON in declared tuple order. Run domain `ZOORA_AE013_PAYMENT_RUN_V1` covers one nested identity tuple `(schema_version, model, classification, unit, rng)`, then config, seed, scenario, policy, intentions, intentions_fingerprint, quotes, transfers, observations, queue, final_balances, rounds, metrics, direct. The intention domain is `ZOORA_AE013_PAYMENT_INTENTIONS_V1`; the campaign domain `ZOORA_AE013_PAYMENT_CAMPAIGN_V1` covers schema_version, model, classification, unit, rng, config, runs. Fingerprints themselves are excluded. Native replay regenerates every scenario and rejects forged facts, outcomes and missing/reordered rows even when checksums are recomputed. Hashes do not authenticate external events.

Limits: 1–16 distinct sorted seeds, 1–8 distinct scenarios, all three policies, at most 384 rows, 12–64 profiles divisible by four, 3–24 rounds, 1–64 ordinary requests per round, 1–16 provider slots, and 1–5,000 lifetime quoted agreements. Potential requests, including attacker fixtures, total at most 5,000. Payment window is 1–6 ticks, grace 0–6 and service 1–3, with their sum at most 12. Starting units are 0–10^12; price is 1–10^6. Bounded arrays cap full runs at 5,000 quotes, 10,000 transfers, 20,000 observations/queue events and 24 rounds. The existing 4 MiB TOML, 128 MiB JSON and exclusive Unix 0600 output rules apply. Worst-case replay is synchronous and can be expensive; these are resource bounds, not a service SLA.

The HTML exporter requires native replay, stringifies all numbers, uses text nodes and BigInt, and denies connections/external assets through CSP. Its basic display checks are not native replay or authentication, and downloaded HTML is not signed. CSV fields are enums, nonnegative integers and hashes derived from verified models. Source review, local test results and measured failures are recorded in `VALIDATION_AE013.md`; published-source CI evidence is pinned in the draft PR associated with `feature/ae-013-payment-windows`.
