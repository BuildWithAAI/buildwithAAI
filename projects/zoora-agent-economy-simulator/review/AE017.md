# AE-017: reviewed recovery after paid-work disputes

This is an offline candidate layered on AE-016's shared trust runtime. It models **SYNTHETIC review and appeal fixtures** over noncustodial payment observations. It is separate from the community server and AE-015 reservation scheduler. Reviewer IDs, declared operator labels, customer/worker identity, receipts, reasons, work references and useful-work judgments are not authenticated or evaluated against the outside world.

## Rules implemented

A customer may complain after delivery, or after the work deadline if delivery is missing. The complaint window closes six ticks after customer acknowledgment, or six ticks after the work deadline when no acknowledgment exists. An assigned worker may request a nonresponse review from two through seven ticks after an on-time, fully paid delivery, while the customer has not acknowledged it. Windows are exclusive at the end. These are experimental timing units, not adopted service terms.

A positive outstanding payment is required to open a case. Each contract supports one case, with at most 64 cases per run. A complaint pauses new work and group creation/joining for every assigned worker; it does not establish blame. Existing work and memberships remain. Paid unfinished work also receives a hold once its work deadline passes. The original AE-016 standalone report retains its original behavior and fingerprint.

The configured panel excludes reviewers sharing any declared operator with the customer, any assigned worker or the original work-review authority. Admission requires three distinct remaining reviewer operators, allowing a primary, one backup and an appeal reviewer even if the primary times out. Selection is deterministic for replay. This is a fixture test of declared conflicts, not reviewer authentication, random decentralized selection or hidden-collusion detection.

| Stage | Reference rule |
| --- | --- |
| Initial evidence | Parties may add up to eight distinct references; wait two ticks before a verdict |
| Primary review | Assigned reviewer has four ticks after the evidence window |
| Primary timeout | Assign one backup from another operator; four more ticks |
| Primary decision | Provisional; either party may appeal for three ticks |
| Appeal | New reviewer excludes every primary operator, including a timed-out primary |
| Appeal evidence | Two ticks, within a five-tick appellate deadline |
| Final acceptance | Effective acceptance starts at finalization, then work credit matures for three ticks |
| No primary/appeal decision | Expire unresolved; keep outstanding paid-work exposure visible |

Timers run before commands at the same tick. A late primary cannot replace the backup's decision; an appeal at the closing tick cannot reopen a finalized case. An opener may withdraw before a primary decision. After a decision, the appeal route applies. Raw AE-016 dispute/refund-request/decline commands are refused by this adapter so they cannot bypass case windows and finality.

## Decisions and credit

Every verdict binds a digest of the case, opening reason, party evidence, appeal reason, complete consented work plan, contributions, observed payments/returns, delivery reference and successful delivery tick. A reviewer cannot approve missing delivery, incomplete contributions, an underpaid agreement, returned funds or late delivery. References alone do not demonstrate useful output; the verdict is a declared research input.

Evidence changes before finalization make an old acceptance stale. A later partial return also invalidates usable credit immediately, even when the retained historical ruling was accepted. Case history is preserved. A review can accept an unanswered delivery without inventing customer acknowledgment in the underlying direct-payment transcript.

Final acceptance releases the work slot. Reinstatement of previously confirmed credit waits the maturity interval; unconfirmed work additionally needs the original work-review fixture. Independent current customer review, work-review budgets, artifact reuse checks, owner labels and original tier gates still apply. A collective's exact original work-credit shares are restored proportionally. These are experience counters, not member payments.

A rejected or unresolved case keeps a hold while net paid exposure remains. An observed full **voluntary** return clears that exposure and work slot, but earns no work credit. A partial return is not a completed settlement. The engine never signs, freezes, reverses, seizes or refunds funds, and a verdict never emits a financial receipt. Current policy has no alternative rehabilitation route for expired, rejected or stale cases beyond a full observed return; reopening/mediation needs further work.

## Reproduction

Run from this directory, with Rust 1.99.0 and the committed lockfile:

```sh
cargo test --locked --all-targets
cargo test --locked --release --all-targets
cargo build --locked --release
target/release/zoora-review-market recovery-campaign configs/recovery-campaign.toml NEW_CAMPAIGN.json
target/release/zoora-review-market replay-recovery-campaign NEW_CAMPAIGN.json
target/release/zoora-review-market recovery-csv NEW_CAMPAIGN.json NEW_DATA.csv
python scripts/recovery_audit.py NEW_CAMPAIGN.json
```

Use the `.exe` suffix on Windows. `recovery-run INPUT.json NEW_RUN.json` accepts a custom `RecoveryInput`; `replay-recovery RUN.json` regenerates every accepted and rejected action. The retained `examples/recovery-campaign.json.gz` contains all 15 complete histories; the CSV contains one row per case/assigned worker. Output creation is exclusive. Inputs must be bounded regular files; use trusted local directories.

Run/campaign identities are `zoora-recovery-run/0.1.0` and `zoora-recovery-campaign/0.1.0`, schema 1. SHA-256 hashes domain + NUL + compact ordered UTF-8 JSON. Run domain `ZOORA_AE017_RECOVERY_RUN_V1` covers schema, model, classification, input, journal, cases, events and reportless trust transcript. Campaign domain `ZOORA_AE017_RECOVERY_CAMPAIGN_V1` covers schema, model, classification, config and cases. Verdict domain `ZOORA_AE017_REVIEW_BINDING_V1` covers the ordered 14-element evidence tuple described above. Demo references use `ZOORA_AE017_DEMO_REFERENCE_V1`.

The trust transcript deliberately has no standalone AE-016 report identity: contextual admission and credit depend on the enclosing AE-017 history. Every case event retains its visible action-prefix count so an auditor cannot read evidence from a later action. Hashes detect inconsistent histories; they are not signatures or external proof.

Limits: 4,096 actions, 64 cases, 2,048 case events, eight reviewer fixtures, eight evidence references per case, one backup and one appeal. Original trust limits apply to contracts/groups/profiles/work units. Serialized action cap 16 KiB; config/custom-input cap 4 MiB; report input/output cap 128 MiB. Case admission reserves enough simulation horizon for every allowed review stage. Resource bounds do not establish public availability or adversarial API hardening.

The independent Python audit reconstructs applied case transitions, reviewer/operator exclusions, deadlines, action-prefix evidence bindings, work-credit arithmetic, every outer profile snapshot and financial totals. It shares the existing trust arithmetic auditor. Native replay additionally reproduces rejected attempts, direct-ledger history and the exact fixed demonstration matrix. Neither method proves input truth, review fairness or security of a deployed system.

## Remaining development

Real reviewer enrollment/authorization, reliable work evaluation, owner-wide exposure limits, case reopening/mediation, evidence storage/access, scope-budget repair, public governance, service/scheduler integration, group payouts and deployment remain unfinished. Complaint griefing can pause a worker during review; this milestone bounds the workflow rather than proving that harm is eliminated. No live AAI fee/burn/lock/liquidity rule or native-chain/validator behavior is introduced.
