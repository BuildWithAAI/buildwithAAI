# AE-014 — Capacity authorization before payment

This versioned SYNTHETIC / SIMULATED_UNITS experiment addresses AE-013's paid-but-unstarted requests. It adds a local capacity book that binds a single-use permission to an agreement, payer, provider, amount, send cutoff, observation cutoff and delivery deadline. Tokens are deterministic fixture hashes, not signed capabilities or authenticated wallet ownership. No live payment, custody, forced refund, chain, validator, fee, burn or LP allocation is enabled.

## Run and inspect

From this review directory with pinned Rust 1.99.0 and Python 3.11+:

```sh
cargo build --locked --release
python scripts/run_economy_campaign.py --model authorization --config configs/authorization-campaign.toml --output-dir target/my-authorization-campaign
```

The coordinator retains all full journals, config, progress, campaign JSON, CSV and self-contained HTML. Use a new output directory. Append `--max-new-runs 3` to pause with INCOMPLETE status; continue with `--resume`, identical config bytes and identical executable digest. The runner executes against its checkpoint config copy and checks both inputs before and after each native process and before marking COMPLETE. A replacement or corrupt cache cannot silently finish a mixed campaign. Use one coordinator per trusted directory with local hard-link support; only its own progress is replaced atomically. The default `economy` and separate `payment` modes retain their report semantics.

```sh
cargo run --locked --release -- authorization-campaign configs/authorization-campaign.toml new-campaign.json
cargo run --locked --release -- replay-authorization-campaign new-campaign.json
cargo run --locked --release -- authorization-run configs/authorization-campaign.toml 42 OBSERVATION_LAG EVIDENCE_WINDOW_HOLD new-run.json
cargo run --locked --release -- replay-authorization new-run.json
python scripts/authorization_audit.py new-run.json
cargo run --locked --release -- authorization-csv new-campaign.json new.csv
cargo run --locked --release -- authorization-viewer new-campaign.json new.html
```

Native replay regenerates the entire model, including authorization decisions. The independent Python audit reconstructs capability lifecycles, receipt backing, wallet balances, FIFO starts, capacity and exposure. It must run without Python -O. Neither authenticates external events or assesses useful work. Outputs are exclusive new files; invalid replay prevents export.

## Controlled model

The default matrix has ten seeds, eight scenarios, three policies and **240 unique configurations**. Each run has 24 declared profile IDs, twelve rounds, 36 ordinary intentions per round, four slots per provider, price 1,000 and opening balance 200,000 per profile. There are 103,680 intended ordinary requests across all separate replicas. No new income, market price, gas, slippage, fees, trading or autonomous LLM work is modeled.

The shared AE-013 potential intention generator is read-only reused with identical ChaCha8 draws. Its outcomes remain 60% acknowledged, 10% refund refused, 10% full voluntary return, 10% half return and 10% no delivery. Scenario selection and policy never redraw that plan. All eight scenarios and three policies share an intention fingerprint per seed. AE-014 has different timing and client behavior from AE-013, so raw cross-version counts are not a controlled policy comparison.

Round r begins at `3 + 32r`, its delivery deadline is offset +29 and quotes are metadata at round start. The first third of rounds is normal, middle third stress and final third recovery. Ordinary clients attempt authorization from offset +1, retry refusals each tick, and attempt one payment one tick after their first grant. Their wallet is checked before consuming permission; an insufficient budget is retained on the job without a transfer. All cutoffs are exclusive.

Each grant's send cutoff is issue +2 by default; its observation cutoff is send cutoff +6. Every policy refuses a new grant unless `observe_before + service_ticks < delivery_deadline`: even its last valid observation leaves time for two service ticks and a client acknowledgment. This is an honest-capacity-book assumption, not a production guarantee.

| Policy | Hold before work starts |
| --- | --- |
| UNRESERVED_PAYMENT | No capacity held. A grant lets the client pay into a queue. |
| FUNDING_WINDOW_HOLD | Slot held only until the send cutoff, even if paid evidence is pending. |
| EVIDENCE_WINDOW_HOLD | Slot retained until the observation cutoff; timely backed evidence can start in that held slot. |

At a tick: expire holds/deadlines, run scripted service actions, attempt new grants, check client budgets and consume/send, validate observations, dispatch ready work in observation-validation FIFO order. Ties follow fixture insertion order. Scheduling, capacity checks and send permission do not inspect attack labels. The attack flag selects adversarial fixture behavior and reporting only.

A grant binds all terms and its ordinal into its hash. Same-tick use, unknown token, mismatched terms, exclusive send cutoff and repeated consumption are refused. Only one unresolved permit per agreement is allowed; reissue cannot change its terms. Renewed permits receive different tokens. Client refusal happens before debit in this compliant-client model. The code cannot stop an external wallet from sending independently.

A valid payment fact moves synthetic wallet units once at send time. Available evidence is retained separately and passed to the existing direct agreement adapter, including evidence arriving after the authorization expired. Expiry never reverses a transfer or fabricates a refund. A started job holds capacity until acknowledgment, an accepted full voluntary return or delivery deadline. Partial returns and dispute/refusal do not release the slot. Starting work does not verify its value.

| Scenario | Stress-phase intervention |
| --- | --- |
| NORMAL_DELAY | No shock; evidence arrives one or two ticks after sending. |
| UNPAID_BURST | An attacker fixture batch requests provider capacity first and never pays. Each obtains at most one grant. |
| RENEWING_UNPAID | The same unpaid batch renews expired permission until the latest grant deadline. This deliberately measures reservation starvation. |
| PAID_FLOOD | The attacker batch pays first, occupies slots and never delivers. |
| OBSERVATION_LAG | Ordinary evidence arrives six ticks after sending, within the promised observation window. |
| EVIDENCE_AFTER_EXPIRY | Evidence arrives one tick after its observation cutoff. Payments remain real facts in the synthetic ledger, but cannot authorize work. |
| DUPLICATE_AUTHORIZATION | The same token is consumed twice; the second request is refused before another debit. |
| PROVIDER_OUTAGE | All stress work outcomes become missing, even after paid work starts. |

The burst has one fixture request per potential provider slot. Renewing spam has repeated permits for those same bounded agreement IDs; it is not an exhaustive adaptive or unlimited-identity adversary. Quote and authorization metadata can also saturate. No identity oracle, deposit, penalty, real refund enforcement, signed receipt or useful-work verification is added.

## Metrics, integrity and limits

Reports retain intentions, admitted/refused job quotes, bound permits, every authorization event, transfer fact, observation, final balances, per-round results and the direct adapter transcript. Metrics count all intended ordinary work, quoted/paid/started/acknowledged work, paid work without a start, insufficient budgets, attacker requests/starts, grants/refusals, expired holds, duplicate use refusals, late observations and peak occupied slots. Refusals count retry attempts, not unique clients. Summary rows retain twelve sampled stress authorization events; use full journals for the entire history.

Wallet units conserve after each transfer: opening = final. Payments and voluntary returns separately reconcile with direct adapter totals. Paid ordinary requests without a start have a net exposure counter excluding attack jobs; unacknowledged net units include attack fixtures. Neither is independently verified real loss or profit. Round flows sum; peak counters aggregate by maximum. Pooled seeds are separate replicas, not one economy, observed adoption, confidence intervals or economic stability.

Run identity is `zoora-authorization-run/0.1.0`, campaign identity `zoora-authorization-campaign/0.1.0`, schema 1. SHA-256 domains append NUL then compact UTF-8 JSON. `ZOORA_AE014_AUTHORIZATION_RUN_V1` hashes a nested identity tuple (schema, model, classification, unit, rng), then config, seed, scenario, policy, intentions, intention fingerprint, jobs, permits, authorization events, transfers, observations, balances, rounds, metrics, direct report. `ZOORA_AE014_AUTHORIZATION_CAMPAIGN_V1` hashes schema, model, classification, unit, rng, config, rows. Intention domain is `ZOORA_AE014_AUTHORIZATION_INTENTIONS_V1`. Permit domain `ZOORA_AE014_CAPACITY_PERMIT_V1` hashes ordinal, binding, issue tick, send cutoff and observation cutoff. Original synthetic transfer reference domain remains AE-004. Hashes are not signatures or external authenticity proof.

Bounds inherit payment dimensions: 1–16 sorted distinct seeds, 1–8 distinct scenarios, 12–64 profiles divisible by four, 3–24 rounds, 1–64 ordinary tasks, 1–16 provider slots, starting budget 0–10^12 and price 1–10^6. AE-014 additionally caps potential intentions at 2,000; quotes at 2,000; authorizations at 8,000; journal events at 200,000; transfers/observations at 4,000 each; campaign rows at 384. Send window 2–6, grace 0–6, service 1–3, sum at most 12. Journal saturation stops the run without verification; these are resource caps, not availability guarantees. Native TOML/JSON input limits remain 4/128 MiB and outputs at most 128 MiB.

HTML exports require regeneration, stringify exact integers, use text nodes/BigInt and deny external connections/assets. Display checks do not replace replay and HTML is not signed. Chromium 390px checks are not actual iPhone/Safari tests. See [validation](VALIDATION_AE014.md) and [community update](../../../docs/community/AE014_COMMUNITY_UPDATE.md) for measured tradeoffs and source evidence.
