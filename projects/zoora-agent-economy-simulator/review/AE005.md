# AE-005 — Connected agent community simulations

This milestone connects declared agent profiles, creative projects, discussions, service offers and order admission to the AE-004 direct-payment transcript. It produces replayable **SYNTHETIC** research data. It does not run LLM agents, authenticate people or wallets, observe blockchain transfers, or provide a live community service.

Verification status, exact source commits, CI and measured results belong in [VALIDATION_AE005.md](VALIDATION_AE005.md). [Draft PR #14](https://github.com/BuildWithAAI/buildwithAAI/pull/14) is stacked on the existing unmerged AE-004 branch. No automatic merge or deployment is part of this milestone.

## Run locally

Install the repository's pinned Rust toolchain using the [official rustup instructions](https://rustup.rs/). A fresh checkout uses the existing repository:

```sh
git clone --branch feature/ae-005-community-simulations https://github.com/BuildWithAAI/buildwithAAI.git
cd buildwithAAI/projects/zoora-agent-economy-simulator/review
```

For an existing checkout, switch to `feature/ae-005-community-simulations` and enter `projects/zoora-agent-economy-simulator/review`. Run:

```sh
cargo test --locked --all-targets
cargo test --locked --release --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo fmt --all -- --check
cargo run --locked --release -- community-run configs/community.toml BALANCED balanced.json
cargo run --locked --release -- replay-community balanced.json
cargo run --locked --release -- community-csv balanced.json balanced.csv
cargo run --locked --release -- viewer balanced.json balanced.html
cargo run --locked --release -- community-run configs/community.toml SPAM_RESERVATIONS spam.json
cargo run --locked --release -- community-run configs/community.toml PROVIDER_OFFLINE offline.json
cargo run --locked --release -- community-batch configs/community-batch.toml batch.json
cargo run --locked --release -- replay-community-batch batch.json
cargo run --locked --release -- community-csv batch.json batch.csv
```

Open `balanced.html` in a browser. Each output must be a new filename in an existing trusted directory; the CLI refuses overwrites. No wallet, API key, hosting account or service credentials are required. Rust installation and dependency downloads need development-time internet access. The compiled community runner and exported viewer have no network, signer or payment-sending adapter.

The supplied run config uses seed 42, 20 declared agents, 100 intended tasks, a pending limit of 16 per provider, and three posts per agent per tick. The batch repeats three matched scenarios for seeds 7, 42 and 99. Batch seeds override the workload's seed for each run; that original field remains in the source configuration. The JSON summary contains run hashes, and any individual run can be reproduced by changing the run config's seed and selecting its scenario.

TOML permits agents 4–128, tasks 1–500, pending limit 1–32 and posting limit 1–10. Unknown fields fail. TOML integer literals limit nonnegative CLI seeds to `i64::MAX`; the library and JSON preserve full `u64` seeds. Each workload uses 12 simulation ticks. Intentions draw provider, client and scripted outcome from the pinned ChaCha8 implementation. The configured 60/10/10/10/10 outcome split is an input assumption, not a prediction or measured AI success rate.

## What is connected

- A declared operator registers a profile with an agent ID, handle, synthetic wallet label and capability tags. Wallet labels are opaque fixtures, not public addresses or ownership proofs. Handles and all historical handles remain reserved; each wallet label can register once. Capabilities are declarations, not verified qualifications.
- A declared operator can rename or deactivate its profile; an active agent can rename itself. Deactivation limits new participation and order admission. It grants no control over wallet balances, signing or return transfers. These role checks model permissions inside a transcript; they do not authenticate the caller.
- Project owners declare contributors. Contributors can record artifact digests and publish service offers. Public discussion can refer to projects and existing replies in the same context. Membership is an owner declaration, not signed contributor consent. Digests and acknowledgments do not prove useful work.
- An active client accepts an available provider offer. Terms bind the offer's title, price, parties, deadline and criteria digest to one AE-004 agreement. Admission records no payment. It checks global and provider pending limits before creating an agreement.
- Later payment, delivery, acknowledgment, dispute, request, refusal and voluntary-return records pass through the existing direct adapter. Duplicate receipt rejection remains visible. Payment/return observations remain recordable after profile deactivation, within the synthetic adapter's rules.

Provider capacity counts admitted orders with an unexpired deadline, no delivery digest and either no recorded payment or a positive net transfer. Delivery, a complete voluntary return or deadline expiry releases capacity; release never creates a return payment. An artifact digest can release capacity without independently verified delivery quality. Unpaid reservations occupy capacity and can starve legitimate orders. That is a measured limitation, not a solved abuse defense.

The direct adapter accepts bounded `SYNTHETIC_UNIT` receipts from `OFFLINE_FIXTURE_V1`, with no slot and simulated finality. It is quote-bound and rejects some out-of-terms facts. A future real receipt adapter must retain actual observed transfer facts, including overpayments or late transfers, separately from agreement policy. This fixture ledger cannot serve as a complete chain observation ledger.

## Matched scenarios and interpretation

| Scenario | Change to the shared intended workload |
|---|---|
| `BALANCED` | No injected disruption; ordinary provider capacity still applies. |
| `SPAM_RESERVATIONS` | Inject excess posts and fill each provider's pending capacity with unpaid reservations before ordinary requests. |
| `PROVIDER_OFFLINE` | Deactivate every even-numbered provider before admission; surviving providers receive the same intended requests. |

For a seed, all three scenarios share exactly the same intention list and intention fingerprint. Only admitted ordinary orders receive scripted payment/delivery events. Rejected intentions are not counted as paid work. Injected spam orders count toward all accepted orders; they are not silently removed from the denominator.

`acknowledged_delivery_bps` is historical client acknowledgments divided by **all admitted orders**, truncated to integer basis points. It is unavailable when none were admitted. It is neither a quality score nor independently verified economic output. `accepted_order_requests` includes all admission attempts, including spam. `pending_deliveries_at_finish` means positive net payment with no delivery digest; `unpaid_at_finish` means zero recorded payments. These are different measures. Related declared operators are flagged, but undeclared shared control and collusion remain unverified.

Payments = net transferred + voluntary returns. An overdue delivery, dispute or refusal cannot reverse a direct payment. Acknowledgments, contributions and circular payments do not establish productivity or profit. Wallet balances, gas/transaction fees, exchange rates, USD/SOL values and P/L are unavailable in this model.

## Reports, provenance and exports

Report models are `zoora-agent-community/0.1.0`, `zoora-community-run/0.1.0` and `zoora-community-batch/0.1.0`, schema 1. All are classified SYNTHETIC. Event and observation time use simulation ticks. Wall-clock observation/availability timestamps and Solana slots are absent; finality is `SIMULATED_FINAL`, not chain commitment. Transformation version 1 and explicit quality flags identify these limitations.

A manual community report contains final profiles, handle history, projects, posts, offers, order links, nested AE-004 agreements, metrics and both journals. Replay rebuilds state and compares outcomes, links, metrics and fingerprints. A seeded run additionally regenerates the entire scripted scenario and checks its intention list. A batch regenerates every configured seed/scenario combination; it stores run summaries and source fingerprints rather than every raw journal.

Fingerprints hash the domain prefix, a NUL byte and compact UTF-8 JSON of an ordered tuple. The fingerprint field itself is excluded. The domains and fields are:

- `ZOORA_AE005_COMMUNITY_V1`: schema_version, model, classification, provenance, config, agents, projects, posts, offers, orders, direct, metrics, journal.
- `ZOORA_AE005_RUN_V1`: schema_version, model, classification, rng, config, scenario, intents, intentions_fingerprint, community.
- `ZOORA_AE005_INTENTIONS_V1`: the intention array.
- `ZOORA_AE005_BATCH_V1`: schema_version, model, classification, rng, config, runs.

Struct field order, sorted ID collections and the locked dependency/RNG versions fix encoding. AE-004 keeps its separate fingerprint domain. Hash verification establishes internal consistency, not authentic identity or true external events. The independent Python evidence script reconstructs these hashes and reconciles payment totals and order-to-offer bindings.

CSV exporters verify replay before creating output. Order CSV includes source, classification, absent observation/availability time and slot, simulated finality, transformation, seed/scenario, parties, links, ticks, exact amounts, states, fingerprints and quality flags. Batch CSV contains the same source/missingness boundary and per-run counts/amounts; rate denominators are explicit. Missing values are `UNAVAILABLE`, never fabricated zero. CSV fields are quoted; potentially executable spreadsheet text is prefixed with an apostrophe and flagged `CSV_TEXT_GUARD_V1`. This display transformation does not alter the source JSON.

The self-contained dark viewer shows profiles/history, projects/contributors/offers, 20 orders per page, synthetic activity and evidence. It shows at most the first 100 posts; JSON retains the complete history. Arbitrary record IDs, quotes, request amounts and seeds are decimal strings in the browser payload to preserve integer precision. All displayed content uses text nodes. CSP blocks page connections and external assets. Export-time replay verification does not make a downloaded HTML file immutable or signed; rerun Rust verification against the original JSON before relying on a modified snapshot.

## Resource and security boundary

Manual transcripts permit up to 5,000 profiles/orders/offers, 1,000 projects, 10,000 posts, 100 artifact digests per project, 32 historical handles per profile and 50,000 events. The final event slot is reserved for completion. Posting limits count successful posts per agent/tick. Caller-controlled strings are byte-bounded before retention. Unsupported actor/clock/engine-owned events fail; rejected business commands retain outcomes; fatal adapter errors prevent a verified final report.

CLI inputs are bounded regular files: 4 MiB TOML and 128 MiB JSON; outputs are capped at 128 MiB and created with Unix mode 0600. Deserialization rejects unknown fields and bounds major arrays. This is not an OS sandbox or a service SLA. Replay is synchronous, and worst-case bounded transcripts may be expensive. Trusted directories are required; existing file controls do not prevent replacement races in attacker-controlled directories. Avoid secrets in supplied content. Browser tests deliberately alter payloads to check rendering/precision/error handling; those altered files are not source evidence.

## Remaining live work

Authenticated registration and workspace APIs, persistent storage, real agent runtime/tool permissions, an evidence-preserving read-only chain adapter, user-controlled signing design, operational rate limits/moderation and deployment remain separate milestones. A live service needs those controls and its own verification. This milestone supplies reproducible scenario data without purchasing infrastructure or taking customer wallet keys.
