# AE-018: capacity and payment exposure across a declared owner

This offline adapter extends the existing AE-016/017 trust and dispute runtime. It compares identical original action sequences under per-agent admission, owner-wide work counts, and owner-wide counts plus payment exposure and dispute holds. All actors, immutable owner labels, receipts, reviews and useful-work judgments are **SYNTHETIC fixtures**. There is no ownership discovery or authentication in this model.

## Admission rules

An owner has a shared work limit equal to the highest **current** tier among its agents: one, two or four active agreements. The associated payment caps in the reference fixture are 100, 300 and 1,000 atomic `SYNTHETIC_UNIT` units. These are illustrative research parameters, not dollars, AAI valuations, adopted service terms or live policy. Agent credits and limits are not summed across aliases. A tie uses the lowest agent ID as the reported source of the limit.

Each agent must still satisfy its original individual tier, work and membership rules. A reviewed peer does not grant another agent verification or extra individual slots. Existing membership limits remain per agent; AE-018 adds owner-wide work/payment controls, not aggregate owner membership quotas.

| Policy | New contract admission | New group creation or joining |
| --- | --- | --- |
| `AGENT_ONLY` | Original individual checks | Original individual checks |
| `OWNER_COUNT` | Individual checks plus shared owner work count | Original individual checks |
| `OWNER_RISK` | Individual checks plus owner work count, reserved payment budget and owner dispute hold | Individual checks plus owner dispute hold or existing count/payment overage |

Every distinct declared owner assigned to a contract must have room. The entire agreed payment amount is reserved when work opens, before any payment is observed. Creating more agents under a known owner does not create more owner capacity. A group with multiple agents under one owner counts its agreement once for that owner. A group spanning different owners charges the full amount to each owner, conservatively, rather than assuming one member can cover another's obligation.

Reservations remain until the inherited work rules close the commitment: successful acceptance, a fully observed voluntary return, or the deadline for an entirely unpaid agreement. The existing delivery/review rules still govern successful acceptance. A partial return leaves the full notional reservation in place and separately reports the remaining observed net payment. Completed contracts still remain in the historical payment totals. A downgrade can leave existing work above the new limits; it blocks new admission without deleting existing work or payments.

A dispute hold on one agent propagates to the declared owner's new work and new group admission under `OWNER_RISK`. Existing memberships and fulfillment remain. Normal accepted review and credit maturity can restore the owner's admission capacity. The original recovery limitations still apply to unresolved/rejected/stale cases.

Only new commitments are owner-gated. Deliveries, review actions, payment observations and voluntary-return observations continue to the existing validator. An authentic fact is not erased to make a budget look compliant: a valid late payment for an expired unpaid agreement can reactivate exposure and exceed both limits. Malformed or unauthorized facts can still be refused by the original validator. The owner preflight runs first, so its refusal reason may precede a native plan-validation error; an owner decision is not an authorization proof.

## Accounting and replay

`reserved_payment_units` is a full-notional commitment budget. `active_assigned_net_units` describes observed net payment associated with assigned active work. That assignment exposure can appear under several owners and must not be summed as cash or money supply. `active_lead_net_units` attributes the active receipt only to the lead's declared owner. Actual run payment and return totals come from the single existing direct ledger. Work-credit shares remain experience counters; the lead's receipt does not create payments to other group members.

Every original action, including a refused one, is retained in the owner journal. Each action first delegates a recorded `ADVANCE` at its tick to the existing recovery engine, then delegates the actual action if owner admission allows it. Timers therefore expire before same-tick admission. A refused opening consumes no consent or project budget; its clock advance can legitimately expire existing state. Exact sequence links connect both journals. The resulting inner AE-017 report is a genuine standalone replayable recovery report with no hidden owner context. Original AE-016 and AE-017 report fields, identities and reference fingerprints remain unchanged.

New run/campaign models are `zoora-owner-risk-run/0.1.0` and `zoora-owner-risk-campaign/0.1.0`, schema 1. SHA-256 covers the domain, a NUL byte and compact ordered UTF-8 JSON. Run domain `ZOORA_AE018_OWNER_RUN_V1` covers schema, model, classification, input, journal, owners, metrics and recovery. Campaign domain `ZOORA_AE018_OWNER_CAMPAIGN_V1` covers schema, model, classification, config and cases. Hashes and replay detect inconsistent histories; they do not establish real ownership, evidence truth or authorship.

Bounds: 2,048 original actions, at most 4,096 canonical inner actions, 64 owner/agent entries, 512 contracts and the existing recovery case/event bounds. Original action serialization is capped at 16 KiB, config/custom-input files at 4 MiB, and report input/output at 128 MiB. Files must be bounded regular files, outputs must be new, and local directories should be trusted. Canonical decimal strings preserve u128 totals; these bounds do not prove public API availability under hostile load.

## Reproduction

From this directory with the pinned Rust 1.99.0 toolchain and lockfile:

```sh
cargo test --locked --all-targets
cargo test --locked --release --all-targets
cargo build --locked --release
target/release/zoora-review-market owner-campaign configs/owner-campaign.toml NEW_CAMPAIGN.json
target/release/zoora-review-market replay-owner-campaign NEW_CAMPAIGN.json
target/release/zoora-review-market owner-csv NEW_CAMPAIGN.json NEW_DATA.csv
python scripts/owner_audit.py NEW_CAMPAIGN.json
```

Use `.exe` on Windows. `owner-run INPUT.json NEW_RUN.json` accepts a custom `OwnerInput`; `replay-owner RUN.json` regenerates all actions and owner decisions. The retained `examples/owner-campaign.json.gz` includes all 39 complete histories across 13 scenarios. `LARGE_EXACT_TOTALS` uses u64-maximum caps; `HIDDEN_COMMON_CONTROL` deliberately assigns different labels to the aliases. Every comparison within a case receives the exact same configuration and original actions. These fixed demonstrations are controlled examples, not independent trials or estimates of user behavior.

CSV has one row per final owner in each run. Columns prefixed `run_` repeat totals from that run and must not be summed across its owners. Assignment exposures are also non-additive across owners. Import large integer columns as text into spreadsheets or JavaScript tools to avoid floating-point rounding; CSV preserves the original decimal digits. Reports, rather than CSV summaries alone, retain the decision history.

The independent Python auditor reconstructs applied recovery history, profile arithmetic, every owner state, full reservations, lead-only payment attribution and each gate from its prior action prefix. It checks canonical clock/delegation links and matched inputs. Native replay additionally regenerates rejected native attempts and the prescribed demonstration matrix. `owner_evidence.py` exercises the actual CLI, normal/optimized byte equality, retained exports, mutation rejection, bounds and wallet boundaries. Python optimized mode is refused so assertions cannot silently disappear.

## Remaining development

False owner labels still allow hidden common control to bypass these controls. Production ownership verification and reviewer authorization, reliable work evaluation, complaint-griefing defenses, mediation/reopening, scope-budget repair, real evidence storage/access, owner membership policy, group payouts, governance and integration with the community service/reservation scheduler remain unfinished. The module does not hold funds or sign, freeze, reverse or force-return transactions. It introduces no live AAI fee, burn, liquidity deposit, trading strategy execution or Zoora native-chain change. See [validation](VALIDATION_AE018.md) and the [community draft](../../../docs/community/AE018_COMMUNITY_UPDATE.md).
