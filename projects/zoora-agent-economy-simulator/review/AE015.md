# AE-015 — Reservation abuse, wallet quotas and cooldowns

This SYNTHETIC / SIMULATED_UNITS study follows AE-014's reservation-starvation finding. It compares three request rules while retaining the same evidence-window capacity hold. It reuses the existing work, permit, transfer, receipt and direct-agreement engine. AE-014's ordinary generation passes a no-op control with unchanged fixture options; its report schemas and fingerprints remain unchanged.

No production authorization, real wallet identity, custody, freeze, forced refund, signing, penalty, fee, burn, LP allocation or native-chain/validator change is introduced. Wallet IDs and permit hashes are fixtures, not ownership proof.

## Run and reproduce

From this review directory with pinned Rust 1.99.0 and Python 3.11+:

```sh
cargo build --locked --release
python scripts/run_economy_campaign.py --model reservation --config configs/reservation-campaign.toml --output-dir target/my-reservation-campaign
python scripts/run_economy_campaign.py --model reservation --config configs/reservation-long-cooldown.toml --output-dir target/my-long-cooldown
```

The first matrix has **240 configurations**: ten seeds × eight scenarios × three policies. The second has **30 sensitivity configurations**: the same ten seeds and three policies, SLOW_PAYER only, with cooldown changed from eight to sixteen ticks. Both baseline policies are retained as matched parameter controls even though they do not use cooldown. Configurations are unique model inputs; replays, repeated checks and request retries are not extra independent experiments.

Each coordinator keeps every full run, config, progress, campaign JSON, CSV and offline HTML. Start a new directory; append `--max-new-runs 3` for a deliberate INCOMPLETE checkpoint and `--resume` to continue with identical executable/config bytes. Config and executable are checked around every native process and before COMPLETE. Cached runs must regenerate. Use one coordinator per trusted directory with same-filesystem hard-link support. Existing `economy`, `payment` and `authorization` modes retain their behavior.

```sh
cargo run --locked --release -- reservation-campaign configs/reservation-campaign.toml new-campaign.json
cargo run --locked --release -- replay-reservation-campaign new-campaign.json
cargo run --locked --release -- reservation-run configs/reservation-campaign.toml 42 ROTATING_UNPAID QUOTA_COOLDOWN new-run.json
cargo run --locked --release -- replay-reservation new-run.json
python scripts/reservation_audit.py new-run.json
cargo run --locked --release -- reservation-csv new-campaign.json new.csv
cargo run --locked --release -- reservation-viewer new-campaign.json new.html
```

Native replay regenerates both rule decisions and the complete work transcript. Rehashed false decisions, counters, wallet outcomes and missing rows cannot replay or export. The independent audit reconstructs rule decisions from permit history at each request, then checks the shared capability lifecycle, balances, receipts, FIFO, capacity and exposures. It does not regenerate every fixture request or authenticate outside events; use native replay too. Python -O is refused.

## Controlled workload and rules

The nested `authorization` config retains AE-014 dimensions: 24 declared profile IDs, twelve 32-tick rounds, 36 intended ordinary requests per round, four slots per provider, a two-tick exclusive send window, six additional evidence ticks, two service ticks, 200,000 opening units per profile and price 1,000. There is no new client income, market price, gas, slippage or fee. Outcomes remain scripted, not measured autonomous-agent quality.

The potential intention plan is drawn once with the existing pinned generator. All policies, scenarios and sensitivity rows for a seed share the intention fingerprint. Scenario interventions can change actual attack-wallet bindings or client timing without redrawing ordinary demand. Comparisons are within this experiment; unrelated version totals are not a controlled comparison.

| Policy | Additional request rule |
| --- | --- |
| EVIDENCE_HOLD | AE-014's full observation-window capacity hold; no additional quota or cooldown. |
| PENDING_QUOTA | At most one unpaid held permission for the same declared wallet/provider pair. A consumed permission no longer counts as unpaid, even while receipt evidence is pending. |
| QUOTA_COOLDOWN | The same quota, plus refusal until unused-expiry tick + cooldown. A paid permission that expires awaiting evidence does not create an unpaid-expiry cooldown. |

Checks run before the capacity book grants a permission. They receive only tick, payment binding and permit history, without an attack label. Quota refusal takes precedence over cooldown. Pending selection follows permit ordinal; cooldown cites the latest unused expiry, breaking ties by ordinal. The end of cooldown is exclusive: a request exactly at `blocked_until` is eligible for the capacity check. Rule eligibility is not a grant, payment or guarantee of service.

Every evaluated request retains its full binding, tick, sequence, decision, blocking token and cooldown end. A quota/cooldown refusal never debits a wallet. The underlying capacity book still enforces provider limits, one-time consumption and enough remaining time for the last valid observation plus service and acknowledgment. Full holds remain until valid work begins or the observation window expires. A started job retains capacity until acknowledgment, observed full voluntary return or delivery deadline.

At each tick, existing holds/deadlines and scripted work actions run before request checks; grants precede client payment attempts, observations and FIFO work dispatch. A permission paid later in that same tick is still unpaid when earlier request checks run. The audit reconstructs that order and does not use future consumption to excuse a refusal.

| Scenario | Middle-third intervention |
| --- | --- |
| NORMAL_DELAY | Ordinary clients pay one tick after permission; evidence is available one or two ticks later. |
| CONCENTRATED_UNPAID | The renewing attack batch binds every request to one declared attack wallet and never pays. |
| ROTATING_UNPAID | The same batch uses the full bounded attack-wallet pool and repeatedly renews expired permissions. This tests a quota bypass, not unlimited adaptive identities. |
| SLOW_PAYER | Ordinary clients miss their first send cutoff, retain no payment from that refused attempt, then request replacement permission after expiry. Subsequent permissions use normal timing. |
| OBSERVATION_LAG | Evidence is available six ticks after sending, inside the promised window. |
| PAID_FLOOD | Attack fixtures pay, occupy capacity and never deliver. |
| EVIDENCE_AFTER_EXPIRY | Evidence arrives one tick after permission's observation cutoff. Transfer facts remain recorded; work cannot start. |
| PROVIDER_OUTAGE | Stress work starts but all provider outcomes are missing. |

First and final thirds retain normal/recovery behavior. Cooldowns are not reset at round boundaries and can affect recovery. Different declared IDs are not proof of independent owners. The model does not detect common control, authenticate real funds, assess useful work or implement provider accountability. Honest clients can create exactly the unused-expiry history that triggers a cooldown.

## Evidence and interpretation

`WorkTranscript` is shared evidence without its own report identity; the enclosing AE-015 run owns replay. It retains intentions, jobs, permits, authorization events, transfers, observations, final balances, rounds, metrics and the direct transcript. AE-014 continues to emit its original report identity separately.

Additional metrics count evaluated attempts, eligible attempts, quota and cooldown refusal attempts, unused versus paid authorization expiries, expired client sends, peak simultaneous unpaid holds per wallet/provider pair, ordinary wallets with demand/acknowledgment, and minimum acknowledgments among demanded ordinary wallets. Full runs and summaries also retain each demanded ordinary wallet's intended, paid, started and acknowledged counts. These reconcile to the complete ordinary denominator. They measure declared-ID outcomes, not fairness among authenticated people.

Wallet units conserve after every transfer; payments and voluntary returns reconcile with the direct adapter. Paid requests without a start and unacknowledged net units remain visible. Acknowledgment is scripted, not a work-quality assessment. Retry refusal totals are not counts of distinct users. Seed totals are separate replicas, not one economy, forecasts or confidence intervals.

## Integrity and bounds

Run/campaign identities are `zoora-reservation-run/0.1.0` and `zoora-reservation-campaign/0.1.0`, schema 1. SHA-256 hashes a domain + NUL + compact UTF-8 JSON in declared order. Run domain `ZOORA_AE015_RESERVATION_RUN_V1` covers a nested identity tuple (schema, model, classification, unit, rng), config, seed, scenario, policy, intention fingerprint, work transcript, decisions, controls and wallet outcomes. Campaign domain `ZOORA_AE015_RESERVATION_CAMPAIGN_V1` covers schema, model, classification, unit, rng, config and rows. Intention domain is `ZOORA_AE015_RESERVATION_INTENTIONS_V1`. Underlying AE-014 permit and AE-004 transfer-reference domains are unchanged. Hashes are not signatures or owner authentication.

Cooldown is 1–16 ticks, outer scenarios 1–8 distinct, and all nested authorization limits apply: 16 seeds, 384 rows, 2,000 intentions/quotes, 8,000 permissions, 200,000 authorization events, 4,000 transfers/observations and 24 rounds. Rule decisions independently cap at 200,000; wallet outcomes cap at 64. Saturation stops verification. Native TOML/JSON limits remain 4/128 MiB, with exclusive output files capped at 128 MiB. These are resource caps, not availability guarantees.

HTML exports require replay, preserve integers as strings with BigInt display, use text nodes and deny connections/external assets. They are unsigned and their basic display checks do not replace native regeneration. Desktop/390px Chromium testing does not establish actual iPhone/Safari acceptance.
