# AE-012 — Sustained economy simulation campaigns

This extends the existing AE-005 community engine with repeatable **SYNTHETIC** economy experiments. It adds finite agent budgets, an exact stock/flow ledger, opt-in admission controls, eight shocks, recovery observations, full-journal checkpoints and an offline report. All work stays in `BuildWithAAI/buildwithAAI`, stacked on the integrated AE-011 development branch. It does not modify Zoora consensus, validators, native token economics or production wallets.

## Start a campaign

Use the repository's pinned Rust 1.99.0 toolchain and Python 3.11+. From `projects/zoora-agent-economy-simulator/review`:

```sh
cargo build --locked --release
python scripts/run_economy_campaign.py --config configs/economy-campaign.toml --output-dir target/my-economy-campaign
```

This retains every full run in `runs/`, then produces `campaign.json`, `campaign.csv`, `campaign.html` and `progress.json`. Open the HTML locally, including on a phone that can open the file. This is an offline report, not a deployed web service or an iPhone execution test. A compiled binary and an appropriate local machine are needed to run experiments.

To continue after a pause or interrupted process:

```sh
python scripts/run_economy_campaign.py --config configs/economy-campaign.toml --output-dir target/my-economy-campaign --resume
```

Only the exact same config bytes and executable digest can resume. Existing full runs must replay successfully; corrupt files stop the campaign. Completed run files are published atomically with exclusive hard links from staging on the same local filesystem; filesystems without hard-link support fail. Use trusted local directories and one coordinator per directory. This is not a distributed scheduler or a hostile-directory sandbox. Partial staging folders left by abrupt termination are not completed runs. Outputs are not overwritten, except the coordinator's own progress file via atomic replacement. `COMPLETE` is written only after all expected runs agree with regenerated summary rows and all exports succeed. `--max-new-runs 2` deliberately checkpoints early and leaves `INCOMPLETE`.

The small summary-only CLI is also available:

```sh
cargo run --locked --release -- economy-campaign configs/economy-campaign.toml new-campaign.json
cargo run --locked --release -- replay-economy-campaign new-campaign.json
cargo run --locked --release -- economy-csv new-campaign.json new-campaign.csv
cargo run --locked --release -- economy-viewer new-campaign.json new-campaign.html
cargo run --locked --release -- economy-run configs/economy-campaign.toml 42 SHARED_OPERATOR_SPAM OPERATOR_CAP new-full-run.json
cargo run --locked --release -- replay-economy new-full-run.json
```

Output filenames must be new and their parent directories must exist. Summary-only campaigns retain per-run and per-round metrics plus source fingerprints; use `economy-run` or the Python coordinator to retain the complete admissions, community journal, synthetic receipt ledger and final balances.

## Matched design

The reference uses ten seeds × eight scenarios × two admission policies = **160 unique run configurations**. The illustrative fee sensitivity repeats the same workload matrix for another 160, for **320 unique configurations**, each regenerated during verification. Repeated replay and exports are verification work, not additional independent experiments.

Each run has 24 registered profiles: 12 providers, six ordinary clients and six attacker accounts. Every account starts with 150,000 simulated units in the reference, except the budget-squeeze case below. Fixed roles are deliberate: clients do not receive new income and providers do not become clients. Each of 12 rounds has 36 ordinary work requests, a price of 1,000 units and provider capacity eight. The middle four rounds contain the shock; the final four observe recovery. Setup uses ticks 0–1, round r starts at 3+8r, payment occurs immediately after admission at that same tick, delivery/dispute at +2, acknowledgment/refund request at +3, voluntary return/refusal at +4, and the agreement deadline at +6. The final engine completion tick is 98. Simulation ticks are not a real-time throughput, gas or latency model.

ChaCha8 draws the full potential intention plan before admission, including two extra demand blocks per round. Its digest stays identical across scenarios, policies and fee configurations for each seed. The ordinary outcome assumption is 60% client-acknowledged digest, 10% refused return, 10% full voluntary return, 10% half voluntary return and 10% no delivery. Those are scripted input probabilities, not measured agent performance. Stress outcomes override this plan only in the two explicitly described outcome shocks. Only admitted, affordable ordinary work receives a synthetic payment. Rejected intentions are preserved with reasons and never become invented economic activity.

| Scenario | Explicit intervention |
| --- | --- |
| BALANCED | Ordinary demand and scripted outcomes; natural capacity limits still apply. |
| SHARED_OPERATOR_SPAM | Before ordinary demand in stress rounds, attacker accounts sharing one declared operator attempt to fill every provider's capacity without paying. |
| SYBIL_SPAM | Same attack requests, but each attacker declares a separate operator. The model cannot authenticate their common control. |
| PROVIDER_OUTAGE | Every even provider is inactive during stress, then reactivated before recovery. No automatic rerouting or retry. |
| DEMAND_SURGE | Admit the two precommitted extra demand blocks during stress: three times ordinary demand. |
| BUDGET_SQUEEZE | Every account's opening balance is one tenth of the configured amount for the entire run. No automatic replenishment. |
| REFUND_STRESS | Every admitted ordinary task in stress requests its payment back; the provider records a refusal. No funds reverse. |
| DIGEST_ONLY | Every admitted task in stress gets a digest without client acknowledgment. No independent quality claim. |

`BASELINE` uses existing per-provider admission. `OPERATOR_CAP` additionally limits currently unpaid, unexpired reservations across providers to `max_unpaid_per_operator` under a **declared** operator label. It counts all admitted reservations and excludes expired or paid ones. This is a campaign admission controller with its own decision journal; it does not silently change the existing community schema, live service permissions or wallet capabilities. Immediate synthetic payment means affordable ordinary orders do not remain unpaid between requests. Real payment delays, ordering and identity verification need separate experiments.

## Exact accounting and fee assumptions

The reference fee is **zero**. `configs/economy-fee-sensitivity.toml` is an **illustrative research setting**, not an adopted fee or AAI allocation policy. It charges 100 basis points (1%) per admitted ordinary payment. Of that fee, floor 50% is counted as burned and floor 25% as a liquidity budget; the treasury gets the remaining units, including rounding. For a 1,000-unit payment this is a ten-unit fee: five burned, two to the liquidity budget and three to treasury. The split is therefore 50/20/30 after per-payment integer rounding in this example. At price one the computed fee is zero.

Payment moves the quoted amount from the client balance to the provider and deducts the extra fee from the client. A voluntary return transfers only an observed return amount from provider to client. Refusals, disputes, deadlines and account activity switches never move units. Fees do not automatically return with a provider's voluntary return. No liquidity position, AMM reserves, trading, slippage, market price, external demand, USD value, yield or token-floor support is modeled.

After every modeled transfer:

`opening units = agent liquid units + treasury units + liquidity budget units + cumulative burned units`

Every balance remains nonnegative. Payment totals and voluntary-return totals must match the existing direct receipt transcript. The independent Python verifier reconstructs balances and routing from those receipts. Total paid minus voluntary returns is net transferred; it is not profit. A burn decreases modeled remaining units and does not establish economic stability. Reserves are allocations to counters, not deployed liquidity or proof of price support.

## Metrics and interpretation

Every run records admissions, attack requests/admissions, ordinary work intended/admitted/acknowledged, budget refusals, ordinary capacity/unavailable-provider refusals, refused returns, digest-only work, exact payments/returns/fees/stocks and the largest provider account's share of gross payments. Round tables retain normal, stress and recovery denominators. `acknowledged_per_intended_bps` is acknowledged ordinary work divided by all intended ordinary work, truncated to integer basis points. It is not divided by admitted work or inflated by unpaid attacks. Missing denominators are `null` in JSON and `UNAVAILABLE` in CSV.

`unacknowledged_net_units` is outstanding net payment without a client acknowledgment; `undelivered_net_units` is outstanding net payment without a delivery digest. A digest cannot establish quality. Neither metric establishes a realized financial loss. Capacity rejections in `Counts` apply to ordinary work; attacks have their own requested/admitted counts. Operator-limit rejections count all requests hitting that gate. Budget checks precede operator and engine admission checks, so a refusal reason is the first failing gate, not a causal decomposition of every concurrent problem.

The viewer pools numerators and denominators across seeds, reports the lowest per-seed acknowledgment rate and the absolute paired policy difference. Replicas are separate experiments; pooled stock/flow totals must not be interpreted as one economy. It does not invent confidence intervals or extrapolate fixed assumptions into a future adoption forecast. Baseline/capped workload pairs share the same seed; scenarios within a seed and repeated replays are not independent observations.

## Replay, hashes and limits

`zoora-economy-run/0.1.0` and `zoora-economy-campaign/0.1.0`, schema 1, use **SYNTHETIC / SIMULATED_UNITS** and the pinned RNG identifier. SHA-256 hashes the domain, a NUL byte and compact UTF-8 JSON in declared tuple order. The run domain `ZOORA_AE012_ECONOMY_RUN_V1` covers: `(schema_version, model, classification, unit, rng)` as one nested identity tuple; config, seed, scenario, policy, intentions, intentions_fingerprint, admissions, ledger, final_balances, rounds, metrics, community. The intention domain `ZOORA_AE012_INTENTIONS_V1` covers the intention array. The campaign domain `ZOORA_AE012_ECONOMY_CAMPAIGN_V1` covers schema_version, model, classification, unit, rng, config, runs. Fingerprint fields themselves are excluded.

Replay regenerates complete runs and compares the controller journal, ledger, balances, all metrics and nested community state. Full-run replay also invokes existing community verification. Campaign replay regenerates every expected row, catches missing/reordered/forged rows and compares all fingerprints. Recomputed attacker-supplied hashes do not bypass regeneration. Checksums establish consistency, not authenticated external facts.

Bounds: 1–16 distinct sorted seeds; 1–8 distinct scenarios; exactly both policies; 12–64 agents divisible by four; 3–24 rounds; 1–64 ordinary tasks per round; provider and operator limits 1–16; starting balance 0–10^12; price 1–10^6; fee 0–1000 bps; nonnegative burn/liquidity shares totaling at most 10,000 bps. The conservative potential-intention plus attack-attempt budget is at most 5,000 per run, even for configurations selecting fewer scenarios. The matrix has at most 256 rows. Large arrays have bounded deserializers. Inputs retain the existing 4 MiB TOML / 128 MiB JSON limits; unknown fields fail and new outputs use Unix 0600. Full-journal campaigns consume more disk than summary exports. Library/JSON APIs preserve full u64 seeds; TOML CLI literals are limited by TOML's signed integer representation.

The viewer receives all numbers as decimal strings, uses BigInt for amounts and text nodes for content, has no remote assets and a CSP denying connections. Export requires replay. It checks identity and simple conservation before displaying data, but downloaded HTML is neither signed nor a replacement for Rust replay. Browser tests are Chromium desktop/390px checks, not actual iPhone/Safari acceptance.
