# AE-004: direct payments, review allocation, and connected evidence

Zoora's product direction is a general-purpose AI agent economy and creative development community. Users choose agents that operate from their own wallets. The platform supplies coordination, discovery, work records and evidence; it does not hold customer balances, take signing keys, freeze wallets, reverse payments or compel recipients to refund. This module implements an **offline, SYNTHETIC workflow** for that boundary. It is not a live wallet integration, deployed smart contract, production forum or legal determination.

## Run the connected workflow

Check out `feature/ae-004-noncustodial-allocation` from the existing BuildWithAAI repository. Install the repository's pinned Rust 1.99.0 toolchain with rustfmt/clippy. From `projects/zoora-agent-economy-simulator/review`:

```sh
cargo test --locked --all-targets
cargo test --locked --release --all-targets
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo run --locked --release -- direct-demo direct.json
cargo run --locked --release -- replay-direct direct.json
cargo run --locked --release -- viewer direct.json direct.html
cargo run --locked --release -- experiments configs/experiments.toml experiments.json
cargo run --locked --release -- replay-experiments experiments.json
cargo run --locked --release -- viewer experiments.json experiments.html
cargo run --locked --release -- benchmark-allocated allocation-scaling.json
```

Open either generated HTML file locally in a current browser. All outputs must be new files. There are no accounts to create, server processes to start, external assets, dependencies to install for the viewer, wallet requests or network calls. For development, the viewer's HTML/CSS/JavaScript are embedded by the Rust build; rebuilding updates future exports. UI browser checks run in CI using the runner's existing Chrome and Node, not a published website.

## Direct payment semantics

`direct::DirectEngine` tracks agreements, recorded payment receipts, delivery digests, client acknowledgment, disputes, refund requests, recipient refusal and separate voluntary return receipts. It stores **no wallet balance**. Amounts are integers in `SYNTHETIC_UNIT`; aggregate amounts serialize as canonical decimal strings. Delivery/payment/refund remain distinct facts. Receiving a refund is not inferred from an approve/refund verdict or a request.

- A payment is sent directly from the user's agent wallet to the provider's wallet in the intended product design. The present adapter accepts only offline fixtures, not real transfers.
- A refund request changes the coordination record. It does not reverse the original transfer.
- A recipient may decline or ignore a request. The report retains the unresolved request and net payment.
- A voluntary refund needs a separate receipt from the provider to the original payer. Partial receipts are tracked, checked against paid amount, and globally deduplicated by transaction reference. Remaining requested repayment is tracked separately; returns that arrived before a request do not satisfy the new request. Fulfilling a partial request does not falsely label the entire original payment refunded.
- A missed delivery deadline marks the case overdue. It never moves money or freezes either wallet.
- Late delivery remains recordable. A dispute does not establish guilt, fraud, debt, legal entitlement or platform enforcement powers.

The default direct example records 500 units paid, 150 units voluntarily returned, and 350 net transferred. It includes an accepted delivery, a declined refund, a full voluntary refund, no delivery/no refund, and a partial voluntary refund. These are scenario inputs, not real transactions or customer losses. Transaction fees and wallet balances are **unavailable**, rather than fabricated as zero.

Receipt provenance includes source, classification, simulation/availability ticks, optional slot, commitment and transformation version. The fixture adapter requires `SYNTHETIC`, `OFFLINE_FIXTURE_V1`, `SIMULATED_FINAL`, and no real slot. It rejects claims of observed/live/finalized chain evidence. Replay verifies internal consistency; it does not authenticate wallet ownership or verify a blockchain transaction. A future read-only adapter must validate chain/network, successful execution, asset/mint, amounts, payer/payee, attribution, slot, finality, availability and duplicate identity before producing chain-backed facts. Its signing executor must remain outside this reporting library and under independently authorized user controls. No seeds, private keys, signing RPCs or transaction send APIs are present here.

Legal responsibility cannot be inferred from a configuration flag or a custody label. The module documents software powers and evidence; jurisdiction-specific obligations require separate analysis of the actual service.

## Preserve historical research

AE-001, AE-002 and AE-003 remain separate reproducible models. The older escrow engine is a **synthetic research comparison**, not the production custody model or a claim that direct transfers can be refunded. Its automatic deadline refunds apply only inside that hypothetical escrow ledger. Historical report identities, defaults and golden vectors are preserved.

AE-004 adds `ReviewEngine::with_allocation(review, allocation)` to that research comparison. `POST_ALLOCATED` lets the engine choose the primary reviewer; callers cannot choose an arbitrary reviewer with legacy `POST` in the allocated mode. Primary selection excludes the client's declared operator. The existing accept boundary excludes workers from both client and primary operators. Configure a reviewer pool appropriate to known worker roles; selection does not promise availability of a future unknown worker. Appeals exclude client, worker and primary operator. If no independent operator exists, or eligible operators are at capacity, the request is rejected without fabricating a reviewer.

Each candidate is ranked by `(operator active assignments, operator lifetime assignments, operator ID, account active assignments, account lifetime assignments, account ID)`. The operator capacity is shared by all declared aliases. Extra accounts therefore do not increase an operator's weight, though false undeclared identities remain possible. Assignments are reserved only after successful escrow funding (primary) or valid appeal acceptance. They release after the corresponding decision, cancellation, pre-delivery failure or expiry. Capacity means pending review work, not wallet freezing or locked platform funds. Settlement failure still follows the original research deadline logic.

Allocation reports use a separate `zoora-review-allocation/0.1.0` identity. Their nested review snapshot has the allocated policy identity and must be verified through `replay-allocated`, not as a legacy report. Allocation assignment/release records, operator peaks, decision concentration, refusals, operations and escrow accounting are reconstructed during replay.

## Five matched experiments

`seed` and `tasks` (1–500) define a bounded suite. Every experiment contains its exact logical intentions and an independent intentions hash. Legacy and allocated runs share those intentions and financial inputs; reviewer identities and rejected admissions follow each policy. Reports re-execute the operation history and regenerate the entire suite before verification succeeds.

| Experiment | What it tests |
| --- | --- |
| Balanced | Lowest-ID concentration versus least-loaded declared operators. |
| Declared aliases | Nine accounts share one reviewer operator; allocation weight is unchanged. |
| Capacity stress | Two simultaneous pending assignments per operator; primary overflow rejects before funding. |
| Collusion attempts | Conflicting worker roles and unauthorized verdicts are rejected. Hidden collusion between different declared operators is not detected. |
| Spam / missing reviews | Twenty-four nonresponsive tasks arrive first, occupy capacity and expire. Starvation is measured, not claimed solved. |

A fixed bounded benchmark processes 5,000 concurrent tasks with 100, 1,000 and 10,000 accounts. Timings are CI samples, not real agent productivity, transaction throughput or a service guarantee.

## Viewer and security boundary

The Rust `viewer` command fully verifies supported direct, legacy review, allocation or experiment reports before creating output. Its standalone responsive dark interface provides policy selection, operator decision distribution, accounting, searchable/paginated cases, status filters and evidence digests. Financial totals use `BigInt` in JavaScript. Direct views show payment records and actual voluntary returns; research views label their escrow mode.

Export verification is a statement about the original input at generation time. The HTML is not signed or tamper-proof. Editing it invalidates that claim; reverify the original JSON. Titles and labels render as text, embedded JSON escapes HTML delimiters, and a hash-based CSP blocks connections and unapproved scripts/styles. Embedded assets and the template normalize CRLF/CR to LF before hashing, so Windows checkout line endings cannot invalidate the browser policy. The viewer never imports arbitrary reports itself or asserts chain verification. The CLI rejects oversized and non-regular inputs and refuses existing output files; it is not an OS sandbox or a race-proof facility for hostile shared directories.
