## Build sequence before connecting real value

1. **Finish the two real PCs.** The administrator privately retrieves bootstrap access through the authenticated hosting account. Provision the operator and enroll two distinct user-controlled wallets using message signatures. Keep seed phrases and private signing keys out of chat, the service, GitHub and model context. Keep each PC's model on numeric loopback; keep its bearer file under verified private OS permissions. Follow [two-PC setup](TWO_AGENT_PILOT.md), replacing the old example origin with the exact deployed origin above. Run direct pinned preflight, one supervised task per PC, then GET-only [task review](PILOT_TASK_REVIEW.md). Do not accept public IDs copied from an unverified endpoint to silence a mismatch.
2. **Prove operations.** Verify host account MFA and least-privilege access, review connected GitHub/Railway permissions, and protect the release branch. Establish secret-redacted alerts for downtime, denied access, storage pressure, expired credentials and unresolved work. Take encrypted off-host backups using the application's supported snapshot flow; verify an isolated restore and document who can stop/revoke access. A volume and green healthcheck do not provide these guarantees.
3. **Specify settlement invariants before implementation.** Choose the exact supported chain/cluster, assets/programs/mints, raw-unit precision, payees, fees, authorization limits, quote lifetime, finality policy and refund obligations. Freeze an order's terms and recheck authorization immediately before dispatch. Agents may propose actions; a separate policy-controlled signer must constrain the exact approved instructions. The website, model worker and treasury signer must not share unrestricted keys. Treasury custody/approval arrangements need explicit owner decisions and independent review.
4. **Implement durable receipt consumption and accounting.** The verifier's `receipt_key` explicitly says `DOWNSTREAM_DURABLE_UNIQUE_CONSTRAINT_REQUIRED`. Define durable unique constraints for network/transaction receipt and order fulfillment, plus balanced accounting in raw units. Receipt consumption, ledger entries and fulfillment/outbox intent must commit atomically; a durable idempotent consumer handles downstream delivery. Concurrent consumers, duplicate receipts, conflicting terms and process death between each commit/send boundary must never double-credit or double-fulfill. This is required future work, not a claim about the current sandbox ledger.
5. **Implement uncertain-outcome handling before real dispatch.** Persist approved terms, attempt identity and signed transaction identity before submission. A transport timeout is `UNKNOWN`, not proof of failure. Reconcile the original transaction/provider identity without automatically creating a replacement. For recent-blockhash Solana transactions, track the returned last-valid block height and inspect status/expiration before seeking authorization for any replacement; durable-nonce transactions need their own rules. Simulation and RPC acceptance do not establish settlement. Provider disagreement or missing evidence must stop credit/fulfillment and keep the reservation visible.
6. **Release progressively.** Exercise these invariants using disposable local/devnet assets and provider sandboxes, including provider outage, replay, concurrency, failed transaction, stale quote, revoked mandate and restored-state tests. Review wallet instruction displays with the actual vendor extension. Complete independent security review and the applicable operating/legal decisions before a separately authorized, capped real-money canary. Define loss/exposure limits and a tested stop procedure before increasing volume. No amount of ordinary unit-test success justifies connecting the whole economy at once.

The sequence follows the existing repository's custody boundary; it introduces no token price, membership economics, treasury allocation or native-chain rule. [Virtual Business Spaces issue #19](https://github.com/BuildWithAAI/buildwithAAI/issues/19) and [Development Agent issue #5](https://github.com/BuildWithAAI/buildwithAAI/issues/5) retain their separate unfinished scopes.

## Primary references checked for this review

- [Solana sendTransaction](https://solana.com/docs/rpc/http/sendtransaction): RPC acceptance returns before confirmation and does not guarantee processing. Use status and execution evidence for settlement decisions.
- [Solana confirmation/expiration](https://solana.com/developers/cookbook/transactions/confirmation): use the returned last-valid block height when determining recent-blockhash expiration; keep commitment choices consistent and monitor node freshness.
- [OWASP transaction authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html): bind authorization to transaction data and check it at the execution boundary, with limited validity and replay resistance.

These references inform the future release gates. They do not demonstrate that the missing production transaction system exists.
